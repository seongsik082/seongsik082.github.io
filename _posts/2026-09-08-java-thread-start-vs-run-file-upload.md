# 파일 업로드 검사에서 Java Thread의 `start()`와 `run()`을 구분하는 방법

파일을 올린 뒤의 작업은 왜 `start()`로 시작해야 할까?

**대상 독자:** Java 문법과 간단한 Spring CRUD를 막 익힌 개발자

파일 업로드 기능을 만들다 보면, 업로드가 끝난 뒤 파일 이름을 검사하거나 썸네일을 준비하는 코드를 따로 실행하고 싶을 때가 있다. 이때 `Thread` 객체를 만들고 `run()`을 호출하면 될 것처럼 보인다. 하지만 `run()`은 보통 메서드를 부르는 것과 같고, 새 실행 흐름을 만들지 않는다. 이 글에서는 파일 검사라는 작은 예시 하나로 `start()`와 `run()`이 만드는 차이를 구분한다.

## 1. 오늘의 주제

게시글에 첨부 파일을 올리는 기능을 생각해 보자. 사용자가 올린 파일의 이름을 확인하고, 허용하지 않은 확장자면 저장하지 않으려 한다. 이 검사가 업로드 결과를 결정한다면, 검사는 현재 요청 안에서 끝나야 한다. 반대로 업로드가 성공한 뒤에 남기는 단순 기록처럼, 응답 결과와 관계없는 일도 있다.

초급 개발자는 이 두 일을 모두 “따로 실행하면 빨라지지 않을까?”라고 생각하기 쉽다. 먼저 알아야 할 것은 속도가 아니라 **어느 코드가 어느 실행 흐름에서 실행되는가**이다. `Thread`는 프로그램 안에 실행 흐름을 하나 더 만들 수 있는 클래스다.

이 글을 읽고 나면 `run()`을 직접 부를 때와 `start()`를 부를 때를 코드에서 구분할 수 있다. 또 파일 검사를 정말 뒤로 미뤄도 되는지, 아니면 현재 요청에서 끝내야 하는지를 판단할 수 있다.

## 2. 핵심 개념

작은 예시부터 보자. `Runnable`은 “나중에 실행할 코드 묶음”을 표현하는 인터페이스다. 파일 이름 검사 코드를 `Runnable`에 담아 둘 수 있다. 아직 실행은 시작하지 않는다.

`new Thread(fileCheck)`는 그 코드 묶음을 실행할 `Thread` 객체를 만든다. 객체를 만들었다고 코드가 즉시 실행되지는 않는다. 책을 책상 위에 올려두었다고 읽기가 시작되지 않는 것과 같다.

`start()`는 새 실행 흐름을 시작하도록 Java에 요청하는 메서드다. Java 공식 문서도 `start()`가 해당 스레드의 실행을 시작하도록 예약하고, 새 스레드가 실행을 시작시킨 흐름과 동시에 동작한다고 설명한다. 반면 `run()`은 스레드가 실행될 때 수행할 메서드다. 우리가 `run()`을 직접 호출하면 현재 실행 중인 코드가 그 메서드를 그냥 이어서 실행한다. 새 `Thread`가 생기는 것이 아니다.

## 3. 내부 동작 원리

파일 업로드 요청에서 아래 코드가 실행된다고 가정하자. 정확한 출력 순서는 매번 같다고 기대하면 안 된다. 두 실행 흐름이 함께 움직이기 때문이다.

1. 현재 실행 흐름이 파일 이름 검사 코드를 `Runnable`로 준비한다.
2. `new Thread(...)`가 검사 작업을 맡을 객체를 만든다. 이 시점에는 검사 문장이 아직 출력되지 않는다.
3. `worker.start()`를 호출하면 Java가 새 실행 흐름에서 `run()` 내용을 실행하도록 예약한다.
4. 기존 실행 흐름은 `start()` 호출 뒤의 다음 줄을 계속 실행할 수 있다.
5. 새 실행 흐름은 파일 검사 코드를 끝내면 종료한다.

따라서 `start()` 다음에 적은 로그가 검사 로그보다 먼저 보일 수도, 나중에 보일 수도 있다. 어떤 줄이 먼저 출력될지는 프로그램이 약속하지 않는다. 결과가 반드시 필요하다면 “따로 실행할까?”보다 “이 작업이 업로드 성공 여부를 결정하는가?”를 먼저 물어야 한다.

`worker.run()`으로 바꾸면 3번이 사라진다. 현재 실행 흐름이 `run()` 안의 코드를 끝까지 처리한 뒤에야 다음 줄로 간다. 그래서 로그 순서는 읽기 쉬워질 수 있지만, 비동기로 실행한 것은 아니다.

## 4. 실제 코드

아래 코드는 Java에서 바로 실행할 수 있는 학습용 예시다. 실제 파일을 저장하지 않고, 파일 이름을 검사하는 위치만 보여 준다.

```java
public class FileCheckDemo {
    public static void main(String[] args) {
        String fileName = "profile.png";

        Runnable fileCheck = () -> {
            boolean imageFile = fileName.endsWith(".png");
            System.out.println("파일 검사 결과: " + imageFile);
        };

        Thread worker = new Thread(fileCheck, "file-check-worker");
        worker.start();

        System.out.println("업로드 요청의 다음 작업을 처리합니다.");
    }
}
```

`fileCheck`에는 파일 검사 방법만 들어 있다. `worker`를 만들 때 이름을 붙인 것은 로그를 볼 때 어떤 작업인지 구분하기 쉽기 때문이다. 핵심은 `worker.start()`다. 이 한 줄이 새 실행 흐름에서 `fileCheck`의 내용을 실행하게 한다.

학습 목적으로 `worker.run()`으로 바꿔 실행해 보면 차이를 볼 수 있다. 두 문장은 모두 출력되지만, `run()`일 때는 파일 검사 결과가 먼저 출력된 뒤 다음 문장이 출력된다. 단, 이 코드의 목적은 순서를 외우는 것이 아니다. `run()`은 일반 메서드 호출이고, `start()`는 새 실행 흐름을 시작한다는 차이를 확인하는 것이다.

## 5. 실제 서비스 적용

작은 Spring 파일 업로드 서비스에서는 먼저 작업을 둘로 나눈다. 파일 크기, 확장자, 로그인한 사용자의 권한처럼 업로드 성공 여부를 바꾸는 검사는 요청 처리 중에 끝낸다. 검사가 늦게 끝나면 허용하지 않은 파일을 저장한 뒤 응답을 성공으로 보내는 문제가 생길 수 있다.

반대로 업로드 완료 뒤에 남기는 통계나 알림처럼, 사용자가 바로 받을 응답과 관계없는 작업은 별도로 처리하는 선택을 할 수 있다. 그렇다고 Controller 안에서 요청마다 `new Thread(...)`를 만드는 것은 실제 서비스에 맞지 않는다. 작업 수를 관리하기 어렵고, 오류를 모아 보기도 어렵기 때문이다. Spring 서비스에서는 프레임워크가 관리하는 비동기 작업 기능이나 메시지 기반 처리처럼, 작업을 관찰하고 제한할 수 있는 방법을 선택한다.

처음 확인할 것은 로그 한 가지면 충분하다. 업로드 요청을 구분하는 값과 작업 이름을 함께 남긴다. “파일 저장 성공” 로그가 “확장자 검사 실패” 로그보다 먼저 나왔다면, 검사를 별도 작업으로 잘못 분리했는지부터 살핀다. 테스트에서는 허용하지 않은 확장자의 파일을 넣고, 저장 메서드가 호출되지 않았는지를 확인하는 편이 더 중요하다.

## 6. 흔히 발생하는 문제

### 1) `run()`을 호출하고 비동기라고 생각하는 경우

현상은 화면이나 로그가 예상보다 순서대로만 진행되는 것이다. 원인은 `run()`이 새 실행 흐름을 시작하는 명령이 아니라 일반 메서드 호출이기 때문이다. 첫 확인 지점은 `Thread` 객체를 만든 뒤 실제로 `start()`를 호출했는지다. 독립적으로 처리해도 되는 작업이라면 `start()`의 의미를 이해한 뒤, 서비스에서는 관리되는 비동기 처리 방법으로 옮긴다.

### 2) `start()` 뒤 로그 순서를 확정된 순서로 믿는 경우

현상은 어떤 날은 검사 로그가 먼저 보이고, 다른 날은 다음 작업 로그가 먼저 보이는 것이다. 원인은 두 실행 흐름의 실행 순서를 코드가 보장하지 않기 때문이다. 첫 확인 지점은 두 로그가 서로 다른 작업 이름에서 나왔는지다. 업로드 결과에 꼭 필요한 값이라면 별도 `Thread`로 보내지 말고 현재 요청에서 검사한다. 꼭 기다려야 하는 별도 작업이라면 완료를 기다리는 규칙을 명확히 둬야 한다.

### 3) 요청마다 `new Thread(...)`를 만드는 경우

현상은 파일 업로드 코드 곳곳에 `new Thread`가 반복해서 보이는 것이다. 원인은 학습용 코드의 편리함을 서비스 구조에 그대로 가져온 것이다. 첫 확인 지점은 Controller나 Service 안에 직접 생성한 `Thread`가 있는지다. 해결 방향은 작업의 종류와 개수를 관리할 수 있는 Spring의 기능 또는 메시지 처리 방식을 선택하는 것이다. 이 선택도 모든 일을 뒤로 보내라는 뜻은 아니다. 업로드 성공을 결정하는 검사는 현재 흐름에 남겨야 한다.

## 7. 기술 선택의 Trade-off

`Thread`를 직접 만드는 방법은 `start()`와 `run()`의 차이를 배우기에 좋다. 코드가 짧고, 실행 흐름이 하나 더 생긴다는 사실을 눈으로 확인할 수 있다. 하지만 웹 요청마다 직접 만들기에는 작업 개수, 실패 기록, 종료 시점 같은 책임이 코드에 흩어진다.

파일 검사처럼 응답 결과를 바꾸는 일은 현재 요청에서 처리하는 편이 단순하고 안전하다. 사용자는 검사 결과를 바로 받아야 하기 때문이다. 반대로 알림처럼 잠시 늦어져도 업로드 결과가 바뀌지 않는 일은 별도 처리 후보가 될 수 있다. 이때는 직접 `Thread`를 만들기보다 Spring이 관리하는 비동기 기능이나 메시지 처리 방식을 검토한다. 관리되는 방식은 설정과 학습 비용이 늘지만, 작업을 모아서 제한하고 실패를 확인하기 쉽다.

실무에서는 다음 순서로 결정한다. 먼저 이 작업이 응답 성공 여부를 바꾸는지 확인한다. 다음으로 실패했을 때 사용자가 다시 요청해야 하는지 정한다. 그 뒤 현재 요청에서 처리할지, 별도 작업으로 보낼지를 고른다. 마지막으로 별도 작업이라면 직접 `Thread`를 만들지 않고, 팀이 오류와 작업량을 확인할 수 있는 방식인지 검토한다.
