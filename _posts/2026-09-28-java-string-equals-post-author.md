# 게시글 수정 권한에서 String을 `==`로 비교하면 생기는 일

글쓴이 아이디가 같은데도 수정 권한이 없다고 나오는 이유는 무엇일까?

**대상 독자:** Java 문법과 간단한 Spring CRUD를 막 익힌 개발자

게시글 수정 기능에는 “현재 로그인한 사람이 글쓴이인가”를 확인하는 코드가 필요하다. 두 아이디가 모두 `"minsu"`로 보이니 `==`로 비교해도 될 것 같지만, 어떤 요청에서는 통과하고 어떤 요청에서는 실패할 수 있다. 이유는 `==`가 문자열 내용을 비교하는 연산자가 아니라, 같은 객체를 가리키는지 확인하기 때문이다. 이 글에서는 게시글 수정 권한 확인 한 곳에서 문자열을 어떻게 비교해야 하는지 설명한다.

## 1. 오늘의 주제

게시글 번호 10을 수정하려는 요청을 생각해 보자. 서버는 게시글에 저장된 작성자 로그인 아이디와, 현재 로그인한 사용자의 아이디를 비교해야 한다. 둘이 같을 때만 제목과 본문을 바꿀 수 있다.

```http
PATCH /posts/10
```

여기서 핵심은 문자열의 글자 내용이 같은지다. `"minsu"`라는 글자가 두 번 만들어졌다면, 우리는 두 값이 같은 사용자 아이디인지 알고 싶다. 메모리 안에서 정확히 같은 상자를 가리키는지는 권한 판단의 기준이 아니다.

이 주제는 게시글 수정이나 삭제처럼 작성자 확인을 처음 넣을 때 배우면 좋다. 글을 읽고 나면 `==`와 `equals()`를 구분하고, 권한 비교에서 어느 값을 서버가 직접 확인해야 하는지 판단할 수 있다.

## 2. 핵심 개념

Java의 `==`는 참조 타입에서 두 변수가 **같은 객체를 가리키는지** 확인한다. 문자열의 글자 내용이 같아도, 서로 다른 시점에 만들어진 객체라면 `==`는 `false`가 될 수 있다.

`equals()`는 두 객체의 내용이 같은지 비교하기 위한 메서드다. `String`은 글자 내용을 기준으로 `equals()`를 구현해 두었다. 따라서 사용자 아이디, 이메일, 상태 코드처럼 문자열 값의 의미를 비교할 때는 `equals()`를 사용한다.

`Objects.equals(a, b)`는 둘 중 하나가 `null`이어도 비교할 수 있는 도구다. 두 값이 모두 `null`이면 `true`, 하나만 `null`이면 `false`가 된다. 다만 로그인한 사용자 아이디가 `null`인 상태를 정상으로 취급하라는 뜻은 아니다. 인증이 끝난 뒤에는 어떤 값이 반드시 있어야 하는지도 따로 확인해야 한다.

## 3. 내부 동작 원리

게시글 수정 요청이 들어오면 비교는 다음 순서로 이뤄진다.

1. 서버가 인증 정보에서 현재 로그인한 사용자의 아이디를 가져온다.
2. Service가 게시글 번호로 게시글을 조회한다.
3. 조회한 게시글의 작성자 아이디와 현재 사용자 아이디를 준비한다.
4. `Objects.equals(작성자 아이디, 현재 사용자 아이디)`로 글자 내용이 같은지 비교한다.
5. 같으면 수정하고, 다르면 권한 없음으로 처리한다.

`==`를 쓰면 4번에서 내용 대신 객체 위치를 비교한다. 로컬에서 문자열 리터럴을 직접 넣어 테스트하면 우연히 같은 객체처럼 보여 통과할 수도 있다. 그러나 데이터베이스에서 읽은 문자열과 요청 처리 중 만들어진 문자열은 같은 객체라는 보장이 없다. 그래서 권한 코드는 실행 환경에 따라 결과가 바뀌면 안 된다.

또한 현재 사용자 아이디는 요청 본문에서 받지 않는다. 수정 요청에 `authorLoginId`를 넣어 받으면 사용자가 다른 사람의 아이디를 적을 수 있다. 서버가 인증을 거쳐 확인한 사용자 정보와 게시글에 저장된 작성자 정보를 비교해야 한다.

## 4. 실제 코드

아래는 게시글을 수정하기 전에 작성자를 확인하는 학습용 예시다. `currentLoginId`는 인증을 통과한 뒤 서버가 얻은 값이라고 가정한다.

```java
@Service
@RequiredArgsConstructor
public class PostService {
    private final PostRepository postRepository;

    public void update(Long postId, String currentLoginId, UpdatePostRequest request) {
        Post post = postRepository.findById(postId)
                .orElseThrow(() -> new IllegalArgumentException("게시글이 없습니다."));

        if (!Objects.equals(post.getAuthorLoginId(), currentLoginId)) {
            throw new IllegalStateException("수정 권한이 없습니다.");
        }

        post.update(request.getTitle(), request.getContent());
    }
}
```

`findById`로 게시글을 찾은 뒤, `post.getAuthorLoginId()`는 저장된 작성자 아이디를 돌려준다. `currentLoginId`는 현재 사용자의 아이디다. `Objects.equals`는 두 문자열의 내용을 비교하고, 둘 중 하나가 `null`이어도 예외를 바로 내지 않는다.

예시의 예외는 흐름을 보여 주기 위한 것이다. 실제 Spring 서비스에서는 프로젝트의 공통 예외 처리 규칙에 맞춰 404, 403 같은 응답을 정한다. 그래도 비교식 자체는 권한 확인의 핵심이므로, `==`가 남아 있지 않은지 먼저 살피는 편이 좋다.

## 5. 실제 서비스 적용

작은 게시글 서비스에서는 작성자 아이디를 게시글 저장 시점에 서버가 기록한다. 수정 요청 DTO에는 제목과 본문처럼 바꿀 값만 넣는다. 작성자 아이디를 요청 DTO에 넣어 권한을 판단하면, 클라이언트가 값을 바꿔 보낼 수 있다.

로그에는 게시글 번호와 인증된 사용자 번호를 남길 수 있다. 단, 비밀번호나 토큰 같은 민감한 값은 기록하지 않는다. 권한 오류가 늘면 먼저 “어떤 게시글에서 누가 실패했는가”보다 인증 정보가 올바르게 전달됐는지와 작성자 값이 저장 당시부터 맞았는지를 확인한다.

테스트에서는 같은 글자 내용을 가진 서로 다른 `String` 객체를 만들어 비교해 본다. `new String("minsu")`와 데이터에서 읽은 `"minsu"`가 내용 기준으로는 같다고 확인하면 `==` 실수를 잡기 쉽다. 그 다음 다른 사용자 아이디로는 수정 메서드가 예외를 내는지도 확인한다.

## 6. 흔히 발생하는 문제

### 1) 문자열 권한 비교에 `==`를 쓰는 경우

현상은 같은 사용자 아이디인데도 어떤 요청에서는 권한이 없다고 나오는 것이다. 원인은 문자열 내용이 아니라 객체 참조를 비교했기 때문이다. 첫 확인 지점은 `authorLoginId == currentLoginId` 같은 비교식이다. 문자열 값의 의미를 비교해야 한다면 `equals()` 또는 `Objects.equals()`로 바꾼다.

### 2) `값.equals(다른 값)`에서 null 예외가 나는 경우

현상은 권한 확인 중 `NullPointerException`이 나는 것이다. 원인은 왼쪽의 문자열 값이 `null`인데 바로 `equals()`를 호출했기 때문이다. 첫 확인 지점은 작성자 아이디나 인증 정보가 비어 있을 가능성이다. 비교 자체를 안전하게 만들려면 `Objects.equals()`를 쓰고, 인증 정보가 없어서는 안 되는 요청이라면 그 전에 인증 실패로 막는다.

### 3) 요청 본문의 작성자 아이디를 믿는 경우

현상은 수정 요청 JSON에 `authorLoginId`를 바꾸면 다른 글도 수정할 수 있는 것처럼 보이는 것이다. 원인은 권한의 기준을 클라이언트 입력으로 삼았기 때문이다. 첫 확인 지점은 `UpdatePostRequest`에 작성자 아이디가 있는지다. 작성자는 게시글에 저장된 값과 서버가 인증으로 확인한 값을 비교한다.

## 7. 기술 선택의 Trade-off

문자열 비교에 `equals()`를 쓰면 코드가 비교하려는 대상이 “내용”이라는 점을 바로 보여 준다. `Objects.equals()`는 값이 비어 있을 가능성이 있는 경계 코드에서 예외를 줄여 준다. 대신 모든 `null`을 정상처럼 넘기면 데이터가 비어 있는 원인을 늦게 발견할 수 있다.

인증된 사용자 아이디와 저장된 작성자 아이디처럼 반드시 있어야 하는 값은 먼저 인증과 저장 규칙으로 보장하는 편이 좋다. 그 뒤 비교식은 `Objects.equals()`로 안전하게 쓸 수 있다. 숫자 같은 기본형은 `==`로 값을 비교해도 되지만, `String`, `Long`, Entity처럼 객체인 값에는 같은 규칙을 그대로 적용하면 안 된다.

결정은 네 단계로 한다. 먼저 비교 대상이 기본형인지 객체인지 확인한다. 객체의 내용이 중요한 경우 `equals()` 계열을 고른다. 권한 비교라면 클라이언트가 보낸 값이 아니라 서버가 확인한 값을 사용한다. 마지막으로 같은 내용의 서로 다른 객체를 이용해 테스트한다.
