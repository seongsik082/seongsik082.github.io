# 게시글 수정 코드에서 예외를 구분해 던지는 방법

> **부제:** 수정할 수 없는 이유를 코드에 남기면 다음 처리도 분명해진다

**대상 독자:** Java 문법과 간단한 Spring CRUD를 막 익힌 초급 백엔드 개발자

게시글 제목을 수정하는 기능을 만든다고 해 보자. 제목이 비어 있으면 저장하면 안 된다. 사용자가 이미 삭제된 게시글을 수정하려고 해도 저장하면 안 된다. 두 경우 모두 수정에 실패하지만, 실패한 이유는 다르다.

실패 이유를 구분하지 않고 `null`을 반환하거나 `catch (Exception e)`로 조용히 넘기면 Controller는 무엇을 응답해야 하는지 알기 어렵다. Java의 예외는 정상 흐름을 계속할 수 없다는 사실과 그 이유를 호출한 쪽에 전달하는 방법이다.

이 글에서는 게시글 수정 한 흐름에서 입력이 잘못된 경우와 게시글이 없는 경우를 나누어 본다. 복잡한 예외 계층보다, 어느 위치에서 어떤 이유를 알려야 하는지에 집중한다.

## 1. 오늘의 주제

수정 요청이 들어오면 Service는 먼저 제목이 쓸 수 있는 값인지 확인해야 한다. 그다음 수정 대상 게시글이 실제로 있는지 확인한다. 이 두 검사를 통과해야 제목을 바꿀 수 있다.

제목이 비어 있는 것은 요청을 보낸 쪽이 고칠 수 있는 문제다. 반면 게시글이 없는 것은 수정 대상이 사라진 문제다. 둘을 같은 `Exception`으로 뭉뚱그리면 나중에 에러 응답과 로그를 읽기 어려워진다.

글을 읽고 나면 “이 요청은 계속 처리할 수 있는가”를 기준으로 예외를 던질 위치를 정할 수 있다. 또한 Service에서 처리할 일과 Controller에서 응답으로 바꿀 일을 구분할 수 있다.

## 2. 핵심 개념

예외는 코드가 평소 순서대로 계속 실행될 수 없을 때 만드는 객체다. `throw`는 예외를 만들어 위쪽 호출 코드로 보내는 문장이다. 아래 코드에서는 제목이 비었거나 게시글이 없을 때 `throw`가 실행된다.

`IllegalArgumentException`은 메서드에 넘긴 값이 맞지 않을 때 쓸 수 있는 Java 기본 예외다. 제목이 비어 있는 경우처럼, 호출자가 값을 고쳐 다시 요청할 수 있는 상황을 표현하기 좋다.

`PostNotFoundException`은 직접 만든 예외라고 생각하면 된다. 이름에 `Post`와 `NotFound`를 넣으면 로그를 보는 사람도 어떤 문제가 일어났는지 바로 알 수 있다. 예외 이름을 길게 늘리기보다, 서로 다른 처리 기준이 있을 때만 구분한다.

## 3. 내부 동작 원리

게시글 수정은 다음 순서로 진행된다.

1. Controller가 게시글 ID와 새 제목을 Service에 전달한다.
2. Service가 제목이 `null`이거나 빈 문자열인지 확인한다.
3. 제목이 괜찮으면 Repository에서 수정할 게시글을 찾는다.
4. 게시글을 찾으면 제목을 바꾸고, 찾지 못하면 예외를 던진다.

Service에서 예외가 잡히지 않으면 호출한 Controller 방향으로 전달된다. Spring 애플리케이션에서는 보통 전역 예외 처리 코드가 이 예외를 받아 HTTP 응답으로 바꾼다. 따라서 Service는 “왜 수정할 수 없는지”를 정하고, Controller 쪽은 “그 이유를 어떤 응답으로 보여 줄지”를 정리하면 된다.

예외를 던진 뒤에는 그 아래 줄이 실행되지 않는다. 그래서 제목이 비었는데도 Repository를 조회하거나, 없는 게시글인데 `changeTitle`을 호출하는 일을 막을 수 있다.

## 4. 실제 코드

아래는 Spring Service에서 쓸 수 있는 짧은 예시다. `postRepository.findById`는 ID에 맞는 게시글을 찾고, 없으면 비어 있는 결과를 반환한다고 가정한다.

```java
public void changeTitle(Long postId, String newTitle) {
    if (newTitle == null || newTitle.isBlank()) {
        throw new IllegalArgumentException("제목은 비어 있을 수 없습니다.");
    }

    Post post = postRepository.findById(postId)
        .orElseThrow(() -> new PostNotFoundException(postId));

    post.changeTitle(newTitle);
}
```

첫 번째 `if`문은 제목을 검사한다. `isBlank()`는 공백만 있는 문자열도 비어 있다고 본다. 제목이 맞지 않으면 즉시 예외를 던지므로, 아래 Repository 조회까지 진행하지 않는다.

다음 `orElseThrow`는 게시글을 찾았으면 `Post`를 꺼내고, 없으면 `PostNotFoundException`을 던진다. 마지막 줄은 앞의 두 조건을 통과한 경우에만 실행된다.

`try-catch`는 이 메서드에 꼭 필요하지 않다. 여기서 잡아서 메시지만 출력하고 끝내면 호출한 쪽은 수정 실패를 모를 수 있다. 이 메서드가 해결할 수 없는 문제라면, 이유가 보이는 예외를 던져 위쪽 처리 코드에 맡기는 편이 낫다.

## 5. 실제 서비스 적용

작은 Spring 서비스에서는 게시글 수정, 회원 정보 변경, 예약 취소처럼 “대상이 반드시 있어야 하는 변경 요청”에 같은 기준을 적용할 수 있다. Service는 입력과 대상의 상태를 확인한다. Controller 또는 전역 예외 처리 코드는 예외를 받아 400이나 404 같은 응답으로 바꾼다.

입력이 늘어나면 제목 길이처럼 값 하나만 보는 검사도 많아질 수 있다. 그때 모든 검사를 Controller에 흩어 놓기보다, 변경 규칙이 필요한 Service 또는 요청 DTO에 모으는 편이 찾기 쉽다. 다만 같은 검사를 Controller와 Service에 중복해서 넣지 않도록 역할을 정해야 한다.

문제가 생겼을 때는 테스트를 먼저 확인한다. 빈 제목으로 호출했을 때 `IllegalArgumentException`이 나오는지, 없는 ID로 호출했을 때 `PostNotFoundException`이 나오는지 각각 확인한다. 예외가 다르게 나오면 가장 먼저 예외가 던져진 줄과 Repository의 조회 결과를 본다.

## 6. 흔히 발생하는 문제

### 1) 모든 문제를 `catch (Exception e)`로 잡는 경우

현상은 수정이 실패했는데도 API가 성공한 것처럼 보이거나, 단순한 "수정 실패" 메시지만 남는 것이다. 원인은 원래 예외를 잡은 뒤 원인을 호출자에게 전달하지 않았기 때문이다.

첫 확인 지점은 Service의 넓은 `catch`문이다. 이 메서드에서 해결할 수 없다면 잡지 않고 전달한다. 정말 잡아야 한다면, 복구할 방법이 있는 예외만 잡고 원래 원인을 로그나 새 예외에 남긴다.

### 2) 없는 게시글을 `null`로 돌려주는 경우

현상은 `post.changeTitle(newTitle)`에서 `NullPointerException`이 나는 것이다. 원인은 게시글이 없다는 사실을 확인하지 않고 `null`의 메서드를 호출했기 때문이다.

첫 확인 지점은 Repository 조회 직후다. 조회 결과가 없을 수 있다면 `orElseThrow`처럼 그 자리에서 처리한다. 그러면 오류가 난 줄만 봐도 “게시글을 찾지 못했다”는 이유를 알 수 있다.

### 3) 제목 오류와 없는 게시글을 같은 예외로 만드는 경우

현상은 클라이언트가 제목을 고쳐야 하는지, 주소가 잘못된 것인지 알 수 없는 것이다. 원인은 서로 다른 실패 이유를 같은 예외와 같은 메시지로 처리했기 때문이다.

첫 확인 지점은 예외 메시지와 예외 타입이다. 입력값을 고치면 해결되는 문제와 대상 자체가 없는 문제는 구분한다. 다만 모든 조건마다 새 예외 클래스를 만들 필요는 없고, 응답이나 처리 기준이 달라질 때만 나눈다.

## 7. 기술 선택의 Trade-off

예외를 구분하면 실패 원인을 빠르게 알 수 있다. Service 코드도 “어떤 조건에서 멈추는지”를 위에서 아래로 읽을 수 있다. 전역 예외 처리 코드에서 상황에 맞는 HTTP 응답을 만들기도 쉬워진다.

반대로 예외 클래스를 너무 많이 만들면 이름만 외워야 하고 관리할 파일도 늘어난다. 단순한 입력 오류까지 모두 별도 클래스로 만들기보다 `IllegalArgumentException`처럼 이미 뜻이 분명한 예외를 먼저 쓸 수 있다.

| 상황 | 선택 | 이유 |
| --- | --- | --- |
| 제목이 비어 있음 | `IllegalArgumentException` | 호출자가 값을 고쳐 다시 요청할 수 있다. |
| 수정할 게시글이 없음 | `PostNotFoundException` | 대상이 없다는 이유를 분명히 남긴다. |
| 이 메서드에서 복구할 방법이 없음 | 예외를 위로 전달 | Controller 쪽에서 응답으로 바꿀 수 있다. |
| 바로 해결할 수 있는 문제 | 필요한 범위만 `catch` | 복구 로직을 한곳에 둔다. |

결정은 네 단계면 충분하다. 1) 요청을 계속 처리할 수 있는지 확인한다. 2) 못 한다면 입력 문제인지 대상 문제인지 나눈다. 3) 이 메서드에서 복구할 수 없으면 이유가 보이는 예외를 던진다. 4) 위쪽 코드에서 그 예외를 사용자 응답으로 바꾼다.
