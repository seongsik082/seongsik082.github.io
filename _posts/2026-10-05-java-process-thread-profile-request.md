# 회원 프로필 요청 로그로 Java 프로세스와 스레드 구분하기

한 Spring 서버 안에서 여러 요청이 함께 처리되는 이유

**대상 독자: Java 문법과 간단한 Spring CRUD를 막 익힌 개발자**

회원 프로필 API를 실행했는데 로그에 서로 다른 스레드 이름이 보이면, 서버가 여러 개 실행된 것처럼 느껴질 수 있다. 하지만 보통은 하나의 Java 프로그램 안에서 여러 실행 흐름이 요청을 나누어 처리하는 모습이다. 이 글은 프로필 조회 요청 하나를 기준으로 프로세스와 스레드를 구분한다. 중요한 것은 용어를 외우는 일이 아니라, 로그를 보고 “서버가 여러 개인가, 한 서버가 여러 요청을 처리하는가”를 판단하는 것이다.

## 1. 오늘의 주제

Spring Boot 애플리케이션을 실행하면 운영체제는 Java 프로그램 하나를 실행한다. 이렇게 운영체제가 관리하는 실행 단위를 **프로세스**라고 한다. 같은 애플리케이션이 두 번 실행되면 보통 프로세스도 두 개가 된다.

프로세스 안에는 일을 실제로 진행하는 여러 **스레드**가 있을 수 있다. 스레드는 프로그램 안의 실행 흐름이다. 웹 요청을 처리하는 Spring 서버는 요청이 들어올 때마다 일을 나눠 처리할 스레드를 사용한다. 따라서 프로필 조회 두 번의 로그에 스레드 이름이 달라도, 프로세스 ID가 같다면 한 서버 프로세스 안의 일일 수 있다.

Java와 Spring 코드가 익숙해지기 시작하면, 요청이 동시에 들어왔을 때 로그가 섞이는 일을 만나게 된다. 이 글을 읽은 뒤에는 로그에서 PID와 스레드 이름을 보고 먼저 확인할 위치를 정할 수 있다.

## 2. 핵심 개념

회원 프로필 서비스를 카페라고 생각해 보자. 카페 건물 하나가 프로세스다. 건물 안에서 각 주문을 처리하는 직원이 스레드다. 직원이 여러 명이라고 카페 건물이 여러 개인 것은 아니다. 반대로 다른 건물에 같은 카페를 하나 더 열면 그때는 프로세스가 하나 더 생긴다.

프로세스는 메모리와 열린 파일, 네트워크 연결 같은 자원을 가진다. 스레드는 같은 프로세스 안의 자원을 함께 사용하면서, 각자 어느 코드 줄을 실행 중인지에 대한 흐름을 가진다. 그래서 한 스레드가 회원 A의 프로필을 읽는 동안 다른 스레드는 회원 B의 프로필을 읽을 수 있다.

여기서 꼭 기억할 규칙은 하나다. **인스턴스 필드에 요청별 값을 저장하면 여러 스레드가 그 값을 함께 볼 수 있다.** 프로필 조회의 `memberId`처럼 요청마다 달라지는 값은 메서드 지역 변수와 파라미터로 전달해야 한다. 지역 변수는 호출마다 따로 만들어지므로 다른 요청과 섞일 가능성이 작다.

## 3. 내부 동작 원리

회원 프로필 조회 요청은 아주 단순하게 다음 순서로 흘러간다.

1. 운영체제가 Java 프로세스를 실행하고, Spring Boot가 웹 요청을 받을 준비를 한다.
2. 브라우저가 `GET /members/42` 요청을 보낸다.
3. 웹 서버가 준비된 작업 스레드 중 하나에 요청 처리를 맡긴다.
4. 그 스레드가 Controller, Service, Repository 코드를 차례로 실행한다.
5. 응답을 보낸 뒤 스레드는 다음 요청을 처리할 수 있다.

어떤 스레드가 요청을 맡을지는 애플리케이션 코드가 직접 정하지 않는 경우가 많다. 사용하는 웹 서버와 설정이 결정한다. 그래서 `http-nio-8080-exec-1` 같은 이름은 환경에 따라 다르게 보일 수 있다. 이름을 외우기보다, 같은 요청의 로그에 같은 요청 식별값을 함께 남기는 편이 더 유용하다.

프로세스 ID, 즉 PID는 운영체제가 프로세스에 붙이는 번호다. 서버를 재시작하면 PID가 바뀔 수 있다. 스레드 이름도 실행 때마다 달라질 수 있다. 따라서 둘은 사용자 ID나 요청 ID처럼 영구적인 업무 데이터로 저장하면 안 된다. 장애를 분석할 때 “어느 실행 중인 서버와 어느 실행 흐름에서 나온 로그인가”를 좁히는 보조 정보로 쓴다.

## 4. 실제 코드

아래 코드는 프로필 조회가 실행되는 프로세스와 스레드를 로그에 남기는 예시다. Java 9 이상에서는 `ProcessHandle.current().pid()`로 현재 프로세스 ID를 얻을 수 있다.

```java
@Service
@RequiredArgsConstructor
public class MemberProfileService {
    private static final Logger log = LoggerFactory.getLogger(MemberProfileService.class);
    private final MemberRepository memberRepository;

    public MemberProfileResponse read(Long memberId) {
        long pid = ProcessHandle.current().pid();
        String threadName = Thread.currentThread().getName();

        log.info("profile read: memberId={}, pid={}, thread={}",
                memberId, pid, threadName);

        Member member = memberRepository.findById(memberId)
                .orElseThrow(() -> new IllegalArgumentException("회원을 찾을 수 없습니다."));
        return MemberProfileResponse.from(member);
    }
}
```

`memberId`는 메서드 파라미터다. 요청마다 메서드가 호출되므로, 다른 요청의 ID를 담아 두는 공용 칸이 아니다. `pid`와 `threadName`도 이 호출 안에서 만든 지역 변수다. 로그를 보면 같은 PID 아래에서 스레드 이름만 달라지는 상황을 확인할 수 있다.

이 코드는 프로세스나 스레드를 새로 만드는 코드가 아니다. 이미 요청을 처리 중인 현재 실행 흐름의 정보를 읽는 코드다. 요청마다 `new Thread(...)`를 만들어 프로필을 조회할 필요는 없다. Spring 웹 서버가 요청을 처리하는 흐름을 이미 제공하므로, 먼저 기존 요청 처리 안에서 코드가 안전한지 확인하는 것이 순서다.

## 5. 실제 서비스 적용

작은 회원 서비스에서는 프로필 조회, 수정, 탈퇴 같은 요청이 같은 Spring 프로세스 안에서 처리된다. 로컬에서 애플리케이션을 한 번 실행했다면 보통 PID도 하나다. 배포 환경에서 인스턴스를 두 개로 늘리면 프로세스가 두 개 이상이 될 수 있고, 각 프로세스 안에는 다시 여러 스레드가 존재한다.

로그가 섞여 원인을 찾기 어렵다면 첫 단계는 모든 로그에 PID를 붙이는 일이 아니다. 먼저 프로필 조회 시작과 실패 로그에 `memberId` 또는 별도의 요청 식별값을 같은 형식으로 남긴다. 그 다음 필요할 때 PID와 스레드 이름을 추가한다. 모든 로그에 스레드 정보만 많이 넣으면, 어떤 회원 요청의 흐름인지 오히려 찾기 어려울 수 있다.

트래픽이 늘어났을 때는 “스레드를 많이 만들면 해결된다”라고 판단하지 않는다. 요청이 느리면 먼저 프로필 조회에서 데이터베이스 호출이 오래 걸리는지, 외부 호출이 있는지, 같은 스레드가 오래 기다리는지를 확인한다. 처음 볼 테스트는 서로 다른 두 회원 ID로 동시에 조회했을 때 응답과 로그의 회원 ID가 섞이지 않는지다.

## 6. 흔히 발생하는 문제

### 1) 요청별 값을 Service 필드에 저장하는 경우

현상은 가끔 다른 회원의 ID가 로그에 찍히거나, 응답이 이상하게 보이는 것이다. 원인은 Singleton Service 하나를 여러 요청 스레드가 함께 사용하기 때문이다. 첫 확인 지점은 `private Long currentMemberId;`처럼 요청 값을 보관한 필드다. 해결 방향은 값을 메서드 파라미터와 지역 변수로 옮기는 것이다.

### 2) 스레드 이름이 다르면 서버가 여러 개라고 생각하는 경우

현상은 로그가 여러 스레드에서 나왔다는 이유만으로 배포가 중복되었다고 판단하는 것이다. 원인은 프로세스와 스레드를 같은 것으로 본 데 있다. 첫 확인 지점은 같은 시간대 로그의 PID다. PID가 같다면 한 프로세스 안의 여러 스레드일 수 있다. 다만 PID만으로 배포 단위를 완전히 판단하지 말고, 인스턴스 이름과 배포 환경 정보도 함께 본다.

### 3) 요청마다 새 Thread를 만드는 경우

현상은 코드가 비동기로 보이지만 예외 처리와 로그 순서가 더 어려워지는 것이다. 원인은 웹 요청 처리와 별개로 스레드를 무분별하게 만들었기 때문이다. 첫 확인 지점은 Controller나 Service 안의 `new Thread(...).start()`다. 단순 프로필 조회는 현재 요청 흐름에서 끝내고, 시간이 오래 걸리는 별도 작업이 생길 때만 Spring의 관리 기능을 검토한다.

## 7. 기술 선택의 Trade-off

프로세스와 스레드를 구분하면 로그와 코드의 책임이 선명해진다. PID는 어떤 실행 중인 서버에서 나온 로그인지 알려 주고, 스레드 이름은 한 서버 안에서 어떤 실행 흐름이 처리했는지 보여 준다. 여러 요청이 함께 들어오는 Spring 서비스에서 특히 유용하다.

하지만 PID와 스레드 이름을 업무 데이터처럼 쓰면 안 된다. 재시작, 배포, 웹 서버 설정에 따라 값이 달라진다. 사용자 행동을 추적하려면 요청 ID나 회원 ID 같은 별도 식별값이 필요하다. 또한 모든 문제를 스레드 수로 해결하려 하지 말고, 느린 SQL이나 네트워크 대기가 있는지 먼저 확인해야 한다.

다음 네 단계로 결정하면 충분하다.

1. 지금 보는 값이 서버 프로세스 정보인지, 요청을 실행하는 스레드 정보인지 구분한다.
2. 요청별 데이터는 Service 필드가 아니라 파라미터와 지역 변수에 둔다.
3. 로그에는 회원 ID 또는 요청 ID를 먼저 남기고, PID와 스레드 이름은 원인 분석이 필요할 때 추가한다.
4. 느린 요청은 새 스레드를 만들기 전에 DB와 외부 호출 대기부터 확인한다.

### 참고한 공식 문서

- [Java SE 21 Thread API](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/lang/Thread.html) — 스레드가 프로그램 안의 실행 흐름이며, `currentThread()`로 현재 스레드를 얻고 `getName()`으로 이름을 읽는 동작을 확인했다.
- [Java SE 21 ProcessHandle API](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/lang/ProcessHandle.html) — `current()`가 현재 프로세스의 핸들을 반환하고 `pid()`가 운영체제가 부여한 프로세스 ID를 반환하는 동작을 확인했다.
