# Java Map으로 예약 번호에 맞는 출석 상태 찾기

> **부제:** 순서대로 찾지 말고, 찾을 기준이 있다면 키와 값으로 연결하기

**대상 독자:** Java 문법과 간단한 Spring CRUD를 막 익힌 초급 백엔드 개발자

예약 관리 화면에서 예약 번호 `R-100`을 받으면 그 사람의 출석 상태를 보여 주어야 한다고 해 보자. 예약 목록을 처음부터 끝까지 보면서 번호가 같은 항목을 찾을 수 있다. 하지만 “예약 번호로 상태를 찾는다”는 일이 계속 나온다면, 번호와 상태를 바로 연결해 두는 구조가 더 읽기 쉽다.

Java의 `Map`은 찾을 기준이 되는 키와, 그 키에 연결된 값을 함께 보관한다. 이 글에서는 예약 번호를 키로, 출석 상태를 값으로 두는 한 가지 예제만 다룬다.

`Map`은 데이터베이스를 대신하는 도구가 아니다. 이 글의 예시는 이미 메모리에 올라온 작은 데이터를 가공하는 학습용 상황이다. 실제 예약 데이터를 오래 보관하거나 여러 서버가 함께 써야 한다면 데이터베이스가 필요하다.

## 1. 오늘의 주제

예약 번호로 출석 상태를 찾는 기능을 생각해 보자. 예약 번호는 각 예약을 구분하는 값이므로 키로 잘 맞는다. 출석 상태는 `RESERVED`, `CHECKED_IN`, `CANCELED`처럼 예약 번호에 연결할 값이다.

`List`는 여러 항목을 순서대로 보관할 때 편하다. 반면 “이 번호의 상태가 무엇인가”처럼 특정 기준으로 찾아야 할 때는 `Map`이 의도를 더 잘 보여 준다. 이 글을 읽고 나면 키와 값이 무엇인지, 키가 없을 때 어떻게 처리할지 판단할 수 있다.

같은 예약 번호를 두 번 넣으면 Map 안에는 한 개만 남는다. 그래서 예약 번호가 정말 하나의 예약만 가리키는지 먼저 확인해야 한다.

## 2. 핵심 개념

`Map<K, V>`에서 `K`는 키의 타입이고 `V`는 값의 타입이다. `Map<String, AttendanceStatus>`는 문자열 예약 번호와 출석 상태를 연결한다는 뜻이다.

`put(키, 값)`은 키와 값을 Map에 넣는다. 같은 키로 다시 `put`하면 새 값이 이전 값을 바꾼다. 따라서 `put`은 단순히 추가만 하는 메서드가 아니라, 같은 키의 값을 갱신할 수도 있다.

`get(키)`는 키에 연결된 값을 돌려준다. 키가 없으면 `null`을 돌려준다. 값이 없을 때 기본 상태를 보여 줄 수 있다면 `getOrDefault`를 쓰면 된다. 하지만 없는 예약을 정상 예약처럼 보여 주면 안 되는 경우에는 기본값 대신 예외나 별도 응답을 선택해야 한다.

## 3. 내부 동작 원리

예약 번호로 상태를 찾는 흐름은 다음과 같다.

1. 출석 상태를 담을 `Map<String, AttendanceStatus>`를 만든다.
2. `put`으로 예약 번호와 상태를 연결한다.
3. 화면이나 Service가 예약 번호를 받는다.
4. `get` 또는 `getOrDefault`로 그 번호에 연결된 상태를 꺼낸다.

예를 들어 `R-100`의 상태를 `CHECKED_IN`으로 바꾸고 싶다면 같은 키 `R-100`으로 다시 `put`한다. Map은 하나의 키에 하나의 값만 연결하므로, 이전 상태는 새 상태로 바뀐다.

여기서 중요한 것은 키 선택이다. 예약자 이름은 같은 이름을 가진 사람이 있을 수 있으므로 키로 위험하다. 예약 번호처럼 겹치지 않도록 만든 값을 키로 쓰는 편이 안전하다.

## 4. 실제 코드

아래 코드는 그대로 실행할 수 있는 Java 예시다. 예약 번호를 넣고, 두 예약의 상태를 찾는다. 없는 예약 번호에는 기본 상태 `NOT_FOUND`를 돌려준다.

```java
import java.util.HashMap;
import java.util.Map;

public class AttendanceMapDemo {
    public static void main(String[] args) {
        Map<String, String> attendanceByReservation = new HashMap<>();

        attendanceByReservation.put("R-100", "CHECKED_IN");
        attendanceByReservation.put("R-101", "RESERVED");

        String status = attendanceByReservation.get("R-100");
        String missingStatus = attendanceByReservation.getOrDefault(
            "R-999", "NOT_FOUND"
        );

        System.out.println(status);
        System.out.println(missingStatus);
    }
}
```

`Map<String, String>`의 첫 번째 `String`은 예약 번호의 타입이다. 두 번째 `String`은 상태의 타입이다. 실제 서비스에서는 상태를 문자열 대신 `enum`으로 만들 수도 있지만, 처음에는 값이 어떻게 연결되는지 보는 것이 우선이다.

`put("R-100", "CHECKED_IN")`은 예약 번호와 상태를 저장한다. `get("R-100")`은 저장한 상태를 가져온다. 반면 `R-999`는 넣지 않았으므로 `get`을 쓰면 `null`이 나온다. 예시에서는 화면에 없는 예약이라는 상태를 보여 주기 위해 `getOrDefault`를 사용했다.

## 5. 실제 서비스 적용

작은 Spring 서비스에서는 Repository가 조회한 예약 목록을 Service에서 Map으로 바꾼 뒤, 예약 번호별 상태를 여러 번 확인할 수 있다. 예를 들어 출석 처리 화면에 보여 줄 예약이 몇 개이고, 각 예약의 상태를 번호로 찾아야 한다면 Map이 도움이 된다.

입력이 늘어나면 모든 예약을 먼저 조회해 Map으로 만드는 것이 맞는지 확인해야 한다. 화면에서 예약 번호 한 개만 필요하다면 Repository에 그 번호로 조회를 요청하는 편이 낫다. Map은 이미 필요한 범위로 가져온 데이터를 서비스 안에서 정리할 때 사용한다.

문제가 생기면 우선 `Map`의 키 목록과 요청으로 들어온 예약 번호를 확인한다. `R-100`과 `r-100`처럼 대소문자가 다르거나 공백이 섞이면 다른 키로 취급될 수 있다. 테스트에서는 넣은 키로 조회했을 때 같은 상태가 나오는지, 없는 키일 때 어떤 결과를 돌려주는지 확인한다.

## 6. 흔히 발생하는 문제

### 1) 없는 키를 조회한 뒤 바로 메서드를 호출하는 경우

현상은 `get` 결과에 메서드를 호출하다가 `NullPointerException`이 나는 것이다. 원인은 해당 예약 번호가 Map에 없어서 `get`이 `null`을 돌려줬기 때문이다.

첫 확인 지점은 `get` 뒤의 코드다. 없는 예약을 기본 상태로 표시해도 된다면 `getOrDefault`를 쓴다. 없는 예약 자체가 오류라면 `null`을 확인하고 예외나 404 응답으로 처리한다.

### 2) 같은 예약 번호를 여러 번 넣는 경우

현상은 이전 출석 상태가 사라지고 마지막에 넣은 상태만 남는 것이다. 원인은 Map이 같은 키를 하나만 가질 수 있기 때문이다.

첫 확인 지점은 `put`을 호출하는 곳과 예약 번호 생성 규칙이다. 상태를 바꾸려는 의도라면 같은 키로 덮어쓰는 것이 맞다. 서로 다른 예약을 저장하려는 의도라면 예약 번호가 중복되지 않게 해야 한다.

### 3) 순서가 필요할 때 HashMap 순회 결과에 기대는 경우

현상은 화면의 예약 목록 순서가 기대와 다르게 보이는 것이다. 원인은 `HashMap`이 항목을 넣은 순서를 보장하지 않기 때문이다.

첫 확인 지점은 Map을 반복해서 화면 목록으로 만드는 코드다. 예약 시간 순서가 필요하면 별도 목록을 정렬하거나, 순서를 보장하는 자료구조를 검토한다. 단순 조회에는 순서가 필요 없다는 점을 먼저 구분한다.

## 7. 기술 선택의 Trade-off

Map의 장점은 키로 값을 찾는 의도가 코드에 분명하다는 점이다. 예약 번호처럼 하나의 대상을 구분하는 값이 있을 때, 목록을 매번 직접 탐색하는 코드보다 읽기 쉽다.

단점은 키가 중복되면 이전 값이 바뀌고, 키가 없으면 `get` 결과가 `null`일 수 있다는 점이다. 또한 화면 표시 순서가 중요하다고 해서 `HashMap`에 그 순서를 기대하면 안 된다.

| 상황 | 선택 | 이유 |
| --- | --- | --- |
| 예약 번호로 상태 하나를 찾음 | `Map` | 키와 값의 관계가 분명하다. |
| 예약을 시간순으로 모두 보여 줌 | `List`와 정렬 | 목록의 순서가 중요하다. |
| 없는 예약도 기본 상태로 표시함 | `getOrDefault` | 기본값을 한곳에서 정한다. |
| 없는 예약은 오류임 | `get` 뒤 명시적 처리 | 없는 키를 조용히 정상으로 만들지 않는다. |

결정은 네 단계면 충분하다. 1) 하나의 값을 구분할 키가 있는지 본다. 2) 키가 하나의 값만 가리키는지 확인한다. 3) 없는 키를 기본값으로 볼지 오류로 볼지 정한다. 4) 순서가 필요하면 Map과 별도로 순서를 관리한다.
