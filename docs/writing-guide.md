# 글쓰기 가이드

이 블로그는 백엔드 개발자 김성식의 포트폴리오 겸 기술 블로그다. 사람이 쓰든 자동화가 쓰든, 새 글은 이 문서를 기준으로 쓴다.
2026-08-14 ~ 10-22 사이 자동 작성된 초급 글 21편이 같은 예제(상품·예약·회원 프로필·게시글·주문)와 같은 틀을 반복해 2026-10-23에 11편으로 합쳐 다시 썼다. 같은 일이 반복되지 않게 하는 것이 이 문서의 목적이다.

## 독자와 목표

- 1차 독자는 채용 담당자와 함께 일할 개발자다. 글을 읽고 "이 사람은 문제를 어떻게 좁히고 검증하는가"가 보여야 한다.
- 2차 독자는 Java·Spring·SQL을 아는 주니어~미들 백엔드 개발자다. 정의 나열이 아니라 판단 기준과 확인 방법을 얻어 가야 한다.

## 주제 우선순위

1. **실무 경험에서 출발한 글**
   `_data/portfolio.yml`에 정리된 경험을 출발점으로 삼는다.
   - 대용량 조회 성능 개선 (실행 계획, JOIN 조건, 인덱스)
   - 대용량 엑셀 다운로드 (XLS 행 제한, Apache POI XLSX·SXSSF 스트리밍, 메모리)
   - 데이터 정합성과 계산 로직 검증 (과거·현재 결과 비교, 기준 데이터 점검)
   - 운영 안정화와 협업 (요청 우선순위, WAS 설정 점검, 장애 복구 절차)
2. **경험 주변의 기술을 깊게 판 글**
   위 경험과 이어지는 SQL·JVM·Spring·HTTP·배포 주제를 다룬다. 예: 실행 계획 읽는 법, 페이징과 대량 조회, 파일 스트리밍 응답, 커넥션 풀, 트랜잭션 경계, WAS 스레드와 타임아웃.
3. **운영·트러블슈팅 심화 글**
   장애 신호, 확인 순서, 재발 방지를 다룬다.

문법 한 가지를 장난감 예제에 붙이는 초급 글은 쓰지 않는다. 기초 개념이 필요하면 실무 주제 글 안에서 필요한 만큼만 설명한다.

## 사실 규칙

- 실무 경험은 `_data/portfolio.yml`과 작성자가 직접 확인해 준 사실만 쓴다. 고객사·내부 시스템 이름, 공개되지 않은 수치는 쓰지 않는다.
- 측정하지 않은 성능 수치, 겪지 않은 장애를 경험처럼 쓰지 않는다.
- 설명용 예제는 서두에 한 줄로 밝힌다.
  예: `> 이 글의 예제는 개념을 설명하기 위해 구성한 코드이며, 특정 서비스의 운영 수치가 아니다.`
- 공식 문서·RFC·Javadoc 링크는 실제로 열어 보고 주장과 맞는지 확인한 것만 단다.

## 예제 도메인

- 업무 시스템 도메인을 돌려 가며 쓴다. 예: 정산·청구 내역, 엑셀 다운로드, 결재 문서, 공지·첨부파일, 야간 배치, 권한 관리, 사용 통계.
- 상품·예약·회원 프로필·게시글·주문은 이미 과하게 쓰였으므로 주 예제로 쓰지 않는다.
- 최근 4편과 같은 예제 도메인, 최근 8편과 같은 핵심 개념은 피한다. 같은 API를 두 편으로 쪼개지 말고 한 편에 묶는다 (예: `@PathVariable` 정상 사용과 오류 처리).

## 글 구조

모든 글에 같은 번호 목차를 강제하지 않는다. "1. 오늘의 주제 … 7. 기술 선택의 Trade-off" 같은 고정 틀이나 "**대상 독자: …**" 줄을 반복하지 않는다. 대신 아래 요소를 빠뜨리지 않는다.

1. 동기: 실제로 마주칠 요청 흐름이나 장애 상황
2. 구체적 산출물 3개 이상: 코드, 설정, SQL, 테스트, 로그·스레드 덤프 발췌 중에서
3. 대안 2개 이상 비교와, 각각을 쓰지 말아야 할 조건
4. 확인 방법: 주니어가 그대로 실행할 수 있는 테스트·명령·쿼리와, 실패했을 때 처음 볼 곳
5. 마무리 체크리스트나 요약
6. `## 참고한 공식 문서` 링크 2~5개

분량은 코드를 뺀 본문 6,000~9,000자를 목표로 한다. 근거가 부족하면 분량을 채우지 말고 게시를 미룬다.

## 형식

- 파일명: `_posts/YYYY-MM-DD-english-slug.md`. 미래 시각으로 쓰지 않는다.
- front matter: `title`, `date`(+0900), `tags`(`Backend` 포함), `excerpt`(150자 이내).
- 본문에 `# 제목`(H1)을 쓰지 않는다. 레이아웃이 제목을 출력한다.
- 목록과 표 앞에는 빈 줄을 둔다. kramdown은 문단에 바로 붙은 목록을 목록으로 렌더링하지 않는다.
- `{{ }}`, `{% %}`를 글자 그대로 보여야 하면 `{% raw %}…{% endraw %}`로 감싼다. GitHub Actions 예제(`${{ github.sha }}`)가 대표적이다.
- 글을 합치거나 주소를 바꾸면 새 글 front matter의 `redirect_from`에 예전 주소(`/posts/<slug>/`)를 남긴다.

## 게시 전 확인

```bash
ruby scripts/check_posts.rb
git diff --check
```

`check_posts.rb`는 형식 규칙 외에 본문 H1, "대상 독자" 고정 줄, 번호 고정 목차도 오류로 막는다. 통과하지 못하면 게시하지 않는다.

## 게시 주기

월·목 오전 9시(Asia/Seoul)에 한 편을 목표로 하되, 위 기준을 채우지 못하면 그 회차는 건너뛴다. 빈도를 지키려고 품질을 낮추지 않는다.
